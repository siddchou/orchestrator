# Phase 3.5 — Edge Cases and Failure Modes

| Scenario | Current Behavior Without Fix | Required Handling | Severity |
|----------|------------------------------|-------------------|----------|
| **Circular dependency** in job definition (A→B→C→A) | Topological sort enters infinite loop or stack overflow | Detect cycle during DAG validation at job launch time. Use DFS with white/gray/black coloring: if a gray node is revisited, report the cycle path to the user. Reject the run before any step executes. | P0 — must fail fast |
| **Self-referencing edge** (A→A) | Step waits on itself via CountDownLatch → deadlock, step never runs | Validate during DAG build: reject any edge where `sourceStepId == targetStepId`. Report as "step cannot depend on itself". | P0 — immediate deadlock |
| **Orphan step** (zero dependencies AND zero dependents) in a multi-step job | With sequential execution it just runs. With DAG, it has no ordering constraint relative to other steps. | Treat as an independent root node with no dependencies. It becomes runnable immediately alongside other root nodes. This is valid — the step executes concurrently with the rest of the DAG. Log a warning at info level: "step X has no dependencies or dependents". | Info only |
| **Template reference to non-existent step** `${step.nonexistent.output.result}` | ParamResolver regex matches but key lookup returns null → downstream executor receives literal `null` in parameter string | Resolve template references during DAG validation phase (before execution). If a referenced step ID doesn't exist in the job definition, reject with "template references unknown step 'nonexistent'". | P0 — fail before execution |
| **Template reference to step that hasn't executed yet** `${step.B.output.result}` from step A where B is downstream of A | This is a back-reference. In DAG terms, it creates an implicit dependency: A needs B's output but B depends on A (directly or transitively). | Detect during validation: build the explicit dependency graph from JOB_STEP_DEPENDENCY AND the implicit dependency graph from template references. If the combined graph has a cycle, reject with "step A references output of step B which transitively depends on A". | P0 — would cause deadlock at runtime |
| **Template reference to job parameter never supplied** `${job.param.API_KEY}` at launch time | ParamResolver returns null → executor receives `null` in command string or argument list | Two modes: (1) **Strict mode (default):** validate that all `${job.param.*}` references are satisfied by the parameters map at launch time. Reject with "missing required parameter: API_KEY". (2) **Lenient mode:** resolve to empty string, log warning. Mode controlled per-job or per-reference via syntax `${job.param.API_KEY?default_value}`. | P1 — should fail fast, not silently corrupt commands |
| **Template reference to step output key that doesn't exist** `${step.B.output.nonexistentKey}` where B succeeded but didn't produce `nonexistentKey` in its StepResult.outputs map | Null resolution → silent data loss in command string | Same as above: strict mode rejects with "step B produced no output key 'nonexistentKey'". Lenient mode resolves to empty. Since step outputs are dynamic (executor-defined), this is harder to validate at plan time — detect at resolve time, not validation time. | P1 |
| **All-ALWAYS-condition step when every upstream is SKIPPED** | Step runs with no meaningful input from skipped steps. If it depends on their outputs via template, those are null. | Define the semantics: ALWAYS means "run regardless of upstream status". SKIPPED upstreams contribute empty outputs to the template context. The step runs normally; if template resolution fails due to missing data, that's a template error (see above), not a skip propagation issue. Document this explicitly so users understand ALWAYS + SKIPPED ≠ automatic skip. | P2 — behavioral clarity |
| **Step produces output referencing another step's output** (chained templating) Step B outputs `{ "path": "${step.A.output.file}/subdir" }` | Template in output values is not resolved — outputs are stored as-is from the executor. If the executor returns a string containing `${...}`, it's literal text, not a template. | StepResult.outputs are raw data from the executor — no templating on outputs. Templating only applies to inputs (parameters passed TO the step). This is by design: outputs should be concrete values. If an executor needs to compose paths from upstream outputs, it receives resolved values via its input parameters and produces a concrete output. | P2 — design decision, document clearly |
| **Step fails AND has ON_FAILURE edge** | Without DAG support, `continueOnFailure=N` breaks the chain. With DAG, the failure should propagate only along edges that match. | When step A fails: (1) Save FAILED status to JobRunStep. (2) For each dependent D with edge condition ON_SUCCESS → mark D as SKIPPED (upstream failed). (3) For each dependent D with edge condition ON_FAILURE → add D to runnable queue. (4) For ALWAYS → same as ON_FAILURE. This is the core of conditional edge semantics. | P0 — core feature |
| **Step fails AND has no matching edges** (only ON_SUCCESS dependents, step failed) | Dependents have no way to run. They should be skipped transitively. | When marking a dependent SKIPPED due to unsatisfied edge condition, recursively mark its dependents as SKIPPED too — unless they have an ALWAYS edge from another path that IS satisfied. This is a graph traversal: for each unsatisfied node, walk downstream and skip unless an alternative satisfied path exists. | P0 — cascading skip logic |
| **Concurrent steps write to same file/resource** | Race condition at the OS level. The orchestrator doesn't control what executors do with filesystem resources. | Document as a user responsibility: concurrent steps should not share mutable external resources unless designed for it. No orchestrator-level locking — that's outside scope. | Out of scope |
| **DAG validation passes but runtime state diverges** (e.g., step crashes without saving result) | Step thread dies, CountDownLatch never releases → downstream waits forever | Each step task runs in a try-finally: finally block always puts a FAILED result in `completedResults` and counts down the step's latch. This ensures downstream steps unblock even if the executor throws an unchecked exception. Set a per-step timeout (configurable, default 30 min) as a backstop. | P1 — liveness guarantee |
| **Template injection attack** `${job.param.MALICIOUS}` where user controls parameter names | If parameter names are user-controlled and used in shell commands without escaping, command injection is possible. | The templating layer resolves values; the executor (ShellExec) is responsible for safe argument handling. Use `Arrays.asList()` style arguments, not string concatenation for shell commands. Document that `${...}` values should be treated as untrusted input in shell contexts. | P1 — security |
