# Phase 6 — Edge Cases and Failure Modes

| # | Scenario | Current Behavior Without Fix | Required Handling |
|---|---|---|---|
| 1 | **OTel exporter endpoint not configured** | Adding `opentelemetry-spring-boot-starter` without `otel.exporter.otlp.endpoint` would cause the SDK to attempt gRPC connection, log warnings on startup, and potentially block bean initialization. | The Spring Boot OTel starter defaults to a no-op exporter when no endpoint is set. **Verify this behavior** during Task 8. If the starter logs noisy warnings, add `otel.java.global-autoconfigure.enabled=false` and rely solely on programmatic spans (which use the no-op tracer). Document in README that tracing is opt-in via environment variable. |
| 2 | **Metric cardinality explosion from unbounded step-type tags** | A plugin registers 500 one-off step types (`custom-step-001`, `custom-step-002`, …). Each creates a unique tag combination in Prometheus, multiplying time series by 4 (status) × 500 = 2000 per timer. Memory and scrape latency degrade. | Implement the cardinality guardrail (Task 4): configurable cap on distinct step types, defaulting to `__other__` beyond the limit. Log a one-time WARN so operators are aware. Document the property in the observability README. |
| 3 | **MDC context leaking across threads in concurrent execution** | Without a `TaskDecorator`, thread-pool threads retain MDC values from the previous step. Step B's logs contain `stepId=1` (from Step A) until Step B overwrites it — or worse, contain stale data if Step B doesn't set MDC. | Use `ObservabilityTaskDecorator` (Task 6): clear MDC before each runnable, restore after. Set step-level MDC inside the runnable's try block. The decorator's finally block guarantees cleanup even on exceptions. |
| 4 | **Prometheus scrape endpoint left unauthenticated** | `/actuator/prometheus` exposes internal metrics (JVM memory, GC pauses, thread counts, custom run/step data) to anyone who can reach port 8080. In a containerized environment without network policies, this is the default route. | The existing `SecurityConfig` likely protects actuator endpoints via Spring Security's default chain. **Verify** during Task 1 that `/actuator/prometheus` requires authentication. If it does (recommended), document in the observability README how to configure Prometheus with basic auth or a bearer token. Provide an optional `orchestrator.metrics.permit-all=true` property that explicitly permits unauthenticated access — for environments using firewall rules instead. |
| 5 | **Step throws exception before MDC is set** | If `findStep()` returns null or config resolution fails before MDC.put(), the error log line lacks step context, making it hard to correlate with the run. | Set MDC fields as early as possible in the `submitStep` callback — immediately after acquiring the semaphore and before any business logic. The TaskDecorator clears stale MDC first, so setting fresh values is safe. |
| 6 | **Run span not propagated to thread-pool step spans** | Without explicit context propagation (`TracerObservation.createScope(runSpan)`), step spans execute on different threads and lose the parent-child relationship. Tracing UI shows orphaned step spans with no run-level parent. | Wrap the `taskExecutor.execute()` lambda body in a scope that attaches the run span's context. This ensures step spans inherit the run span as parent regardless of which thread executes them. |
| 7 | **ObservabilityService recording fails silently** | If the MeterRegistry throws (e.g., Prometheus registry encounters a serialization error), the `recordStepDuration()` call could throw and interrupt step execution. | Wrap all metric recording calls in try-catch at the `ObservabilityService` layer. Log the error at DEBUG level and swallow — metrics failure must never disrupt job execution. This is the "observability must not affect correctness" principle. |
| 8 | **JSON log file grows unbounded on high-throughput runs** | A job with 100 steps, each producing verbose logs, generates megabytes of JSON output per run. The rolling policy caps at 50MB/day × 30 days = 1.5GB, but a single burst could fill disk before rotation triggers. | The existing `SizeAndTimeBasedRollingPolicy` (50MB maxFileSize, 1GB totalSizeCap for the JSON appender) handles this. Verify the cap is appropriately sized for the target environment. Document log retention in the observability README. |
| 9 | **StepResult.executionTime is Duration.ZERO for cancelled steps** | Cancelled and skipped steps record `Duration.ZERO` execution time (see `DagExecutionEngine.java:345`, `DagExecutionEngine.java:392`). This inflates p50/p95 calculations with zero-duration entries. | Acceptable behavior — zero-duration steps are tagged with status=CANCELLED or status=SKIPPED, so dashboard queries can filter them out. Document this in the Grafana dashboard panel queries (filter `status!="cancelled" and status!="skipped"` for latency panels). |
| 10 | **Concurrent runs on same job produce interleaved MDC** | Two runs of the same job triggered simultaneously each set `jobId` and `runId` in MDC. Without thread isolation, one run's logs could show another run's ID. | Each run executes on its own thread (HTTP request thread or scheduler thread), so run-level MDC is naturally isolated. The TaskDecorator handles step-level isolation within a run. No additional action needed — but verify with a concurrent-run integration test. |
