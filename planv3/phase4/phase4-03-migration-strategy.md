# Phase 4 — Migration Strategy

## Flyway V10: JOB_DEFINITION_VERSION table ✅ Implemented

**File:** `src/main/resources/db/migration/V10__add_job_definition_version.sql`

### Forward migration (As Built)

```sql
CREATE TABLE JOB_DEFINITION_VERSION (
    VERSION_ID     NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    JOB_ID         NUMBER(19) NOT NULL REFERENCES JOB_DEFINITION(JOB_ID),
    VERSION_NUMBER NUMBER(10) NOT NULL,
    EXPORT_JSON    CLOB       NOT NULL,
    VERSION_LABEL  VARCHAR2(500),
    CREATED_AT     TIMESTAMP  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CREATED_BY     VARCHAR2(100) NOT NULL,

    CONSTRAINT JDV_JOB_VERSION_UK UNIQUE (JOB_ID, VERSION_NUMBER)
);

CREATE INDEX IDX_JDV_JOB_ID ON JOB_DEFINITION_VERSION(JOB_ID);
```

### Rollback SQL

```sql
DROP INDEX IDX_JDV_JOB_ID;
DROP TABLE JOB_DEFINITION_VERSION CASCADE CONSTRAINTS;
```

### Column Mapping: Plan vs As Built

| Planned Column | Actual Column | Difference |
|---------------|---------------|------------|
| `EXPORT_CONTENT` | `EXPORT_JSON` | Renamed — more descriptive of content type |
| `CHANGED_AT` | `CREATED_AT` | Renamed — version rows are created, not updated |
| `CHANGED_BY` | `CREATED_BY` | Renamed to match `CREATED_AT` naming convention |
| `CHANGE_DESC` | `VERSION_LABEL` | Renamed + repurposed — stores the username who triggered the change (not a free-form description) |

### Rationale

- `VERSION_ID` — identity PK for JPA mapping
- `JOB_ID` — FK to JOB_DEFINITION. No explicit ON DELETE CASCADE; versions are deleted manually via `JobVersionService.deleteVersionsForJob()` called from `JobDefinitionService.deleteJob()`
- `VERSION_NUMBER` — monotonically increasing per job. Enforced unique with `(JOB_ID, VERSION_NUMBER)` constraint
- `EXPORT_JSON` — CLOB storing the full export-format JSON snapshot of the job at that point in time
- `VERSION_LABEL` — stores a descriptive label (e.g., `"john (import pre-update)"`, `"system (rollback from v2)"`)
- `CREATED_AT`, `CREATED_BY` — audit trail for who changed what and when

### Index Strategy

- `IDX_JDV_JOB_ID` — supports `findByJobIdOrderByVersionNumberDesc()` queries
- `JDV_JOB_VERSION_UK` — unique constraint on `(JOB_ID, VERSION_NUMBER)` prevents duplicate version numbers per job

## No existing data migration needed

The version table is empty at creation. Existing job definitions do **not** need to be backfilled into versions because:

1. The feature is new — there's no prior "version history" concept to preserve
2. The first version of each job will be created on the next update/create after deployment (via the version hook in Task 10)
3. If a snapshot of current state is desired as v1, it can be done via a one-time backfill script post-deployment

**Decision:** No backfill migration. Existing jobs get their first version row only when modified post-V10 deployment. This keeps V10 fast and simple — just table creation.

## H2 compatibility

The `GENERATED BY DEFAULT AS IDENTITY` syntax works on both Oracle 19c+ and H2 in Oracle mode (`MODE=Oracle`). The CLOB type maps to `java.lang.String` in JPA on both databases, matching the existing pattern used for `STEP_CONFIG`.

## Flyway ordering

V10 runs after V9 (backfill_step_dependencies). No dependency changes to existing tables — only a new table. Zero risk of blocking existing functionality during migration.

## CLOB size consideration

The `JobVersionService.truncateExportJson()` method caps stored JSON at ~1M UTF-8 chars (`1024 * 1024 / 3`) to prevent CLOB overflow on databases with smaller default lob sizes. This is a safety net — most job definitions will be well under this limit.
