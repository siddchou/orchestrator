# Phase 4 — Migration Strategy

## Flyway V10: JOB_DEFINITION_VERSION table

### Forward migration

```sql
-- V10__create_job_definition_version.sql
CREATE TABLE JOB_DEFINITION_VERSION (
    VERSION_ID      NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    JOB_ID          NUMBER(19) NOT NULL REFERENCES JOB_DEFINITION(JOB_ID),
    VERSION_NUMBER  NUMBER(10) NOT NULL,
    EXPORT_CONTENT  CLOB       NOT NULL,
    CHANGED_AT      TIMESTAMP  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHANGED_BY      VARCHAR2(100) NOT NULL,
    CHANGE_DESC     VARCHAR2(500),

    CONSTRAINT JOB_DEF_VER_JOB_VERSION_UK UNIQUE (JOB_ID, VERSION_NUMBER)
);

CREATE INDEX IDX_JDV_JOB_ID ON JOB_DEFINITION_VERSION(JOB_ID);
```

**Rationale:**
- `VERSION_ID` — identity PK for JPA mapping
- `JOB_ID` — FK to JOB_DEFINITION. When the job is deleted, versions cascade-delete (implicit since no explicit ON DELETE clause; add if needed)
- `VERSION_NUMBER` — monotonically increasing per job. Enforced unique with `(JOB_ID, VERSION_NUMBER)` constraint
- `EXPORT_CONTENT` — CLOB storing the full export-format JSON snapshot of the job at that point in time
- `CHANGED_AT`, `CHANGED_BY`, `CHANGE_DESC` — audit trail for who changed what and when

### Rollback SQL

```sql
-- V10__create_job_definition_version.sql (rollback)
DROP INDEX IDX_JDV_JOB_ID;
DROP TABLE JOB_DEFINITION_VERSION CASCADE CONSTRAINTS;
```

## No existing data migration needed

The version table is empty at creation. Existing job definitions do **not** need to be backfilled into versions because:

1. The feature is new — there's no prior "version history" concept to preserve
2. The first version of each job will be created on the next update/create after deployment (via the version hook in Task 10)
3. If a snapshot of current state is desired as v1, it can be done via a one-time backfill script post-deployment

**Decision:** No backfill migration. Existing jobs get their first version row only when modified post-V10 deployment. This keeps V10 fast and simple — just table creation.

## H2 compatibility

The `GENERATED BY DEFAULT AS IDENTITY` syntax works on both Oracle 19c+ and H2 in Oracle mode (`MODE=Oracle`). The CLOB type maps to `java.lang.String` in JPA on both databases, matching the existing pattern used for `STEP_CONFIG`.

## Flyway ordering

V10 runs after V9 (backfill_step_dependencies). No dependency changes to existing tables — only a new table. Zero risk of blocking existing functionality during migration.
