# Phase 5 — Edge Cases and Failure Modes

| # | Scenario | Current Behavior Without Fix | Required Handling |
|---|----------|------------------------------|-------------------|
| 1 | **Webhook URL unreachable / DNS failure** | `RestTemplate` throws `UnknownHostException` or `ConnectTimeoutException`. Exception propagates uncaught. | Channel implementation catches the exception and wraps in `NotificationException`. Dispatcher's retry loop catches it, waits backoff delay, retries. After 3 attempts, delivery log entry is `FAILED` with the last exception message. |
| 2 | **Slack rate-limiting response (HTTP 429)** | Slack returns 429. Channel sees non-2xx and throws `NotificationException`. | Same retry path as #1. Additionally, log the status code specifically: `"Slack returned 429 — rate limited"`. Consider adding a `Retry-After` header parser in the future; for now, fixed backoff is sufficient. |
| 3 | **SMTP server down** | `JavaMailSender.send()` throws `MailSendException`. | Caught by dispatcher retry loop. After 3 failed attempts (each ~1s apart), delivery log shows `FAILED`. No impact on run completion — the dispatcher runs async via `@Async`. |
| 4 | **Notification dispatch triggered but job was deleted before dispatch completes** | Dispatcher resolves subscriptions by `jobId`, finds them, then tries to send. The `JobRunCompletedEvent` already has all data needed (runId, jobId, jobName, status) — it's a snapshot, not a live reference. | **No special handling needed.** The event is a value object (record), not an entity reference. Even if the job is deleted after the event fires, the notification contains the captured job name and status. Delivery log still references `subscription_id` and `run_id` via FK — these rows may become orphaned if the job is hard-deleted, but that's a data-integrity edge case acceptable for now. |
| 5 | **Exhausted retry attempts** | After 3 failed attempts, the exception is swallowed silently with no record. | Delivery log entry must be updated to `FAILED` with `attempt_count=3` and `last_error` containing the final error message. Logged at WARN level: `"Notification delivery exhausted 3 retries for subscription {id}"`. |
| 6 | **Malformed channel config saved by user** | User saves `channel_config` JSON that's missing required fields (e.g., no `webhookUrl`). Channel throws `NullPointerException` or sends to null URL. | **Validation at save time:** The REST API validates the channel config against the registered schema before persisting. Missing required fields return 400 Bad Request with field-level errors. **Runtime safety:** Channel implementations should check for null required fields and throw `NotificationException("Missing required config field: webhookUrl")` rather than NPE. |
| 7 | **Channel type in subscription no longer registered** | A custom channel implementation was removed (JAR unloaded, bean disabled). Subscription references the now-missing type. | Dispatcher checks `channelRegistry.get(type)` and if empty, marks delivery log as `FAILED` with message `"No channel registered for type: X"`. No exception thrown — logged at WARN level. |
| 8 | **NotificationExecutor thread pool saturated** | Queue is full (100 pending notifications). CallerRunsPolicy kicks in. | CallerRunsPolicy means the calling thread (the run-completion thread) executes the notification synchronously. This blocks run completion briefly but ensures no notification is dropped. Acceptable trade-off: better to delay run completion by a few seconds than lose a notification. |
| 9 | **Run completes with PARTIAL status — should notifications fire?** | `JobRunCompletedEvent` fires for all terminal statuses (SUCCESS, FAILED, PARTIAL, CANCELLED). | Subscriptions filter by the `events` column. If user subscribed to `RUN_SUCCESS,RUN_FAILURE`, a PARTIAL run won't match. This is correct behavior — users explicitly choose which statuses trigger notifications. Document this in the UI. |
| 10 | **Generic webhook payload template references non-existent field** | Template has `{{nonExistentField}}` — resolved to null or literal string. | Template resolver replaces unknown fields with empty string and logs a debug message: `"Unknown template variable: nonExistentField"`. Does not fail the notification — partial resolution is acceptable for generic webhooks. |
| 11 | **Concurrent run completions trigger duplicate notifications** | Two runs of the same job complete nearly simultaneously. Both fire events, both resolve the same subscriptions. | This is correct behavior — each run gets its own notification. The `run_id` in the delivery log distinguishes them. No deduplication needed. |
| 12 | **Email channel with no SMTP configured** | `JavaMailSender` bean doesn't exist if `spring.mail.*` properties are absent (auto-config conditional). | If `spring-boot-starter-mail` is on the classpath but no mail properties are set, Spring auto-config won't create `JavaMailSender`. The `EmailNotificationChannel` bean creation will fail at startup. **Mitigation:** Make the Email channel bean conditional (`@ConditionalOnBean(JavaMailSender.class)`) so it only registers when SMTP is configured. Users who don't configure mail simply can't use email notifications — other channels still work. |
